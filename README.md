# Бронирование переговорной комнаты

Интерфейс бронирования одной переговорной в течение рабочего дня (09:00–18:00): выбор даты, просмотр броней на таймлайне, создание, редактирование и удаление с проверкой бизнес-правил на клиенте и на mock-сервере.

## Быстрый старт

Нужен **Node.js `^20.19` или `>=22.12`** (требование Vite 8).

```bash
npm install
npm run dev      # dev-сервер, http://localhost:5173
npm test         # unit-тесты доменной логики (Vitest)
npm run lint     # oxlint
npm run build    # проверка типов + production-сборка
npm run preview  # просмотр production-сборки
```

Бэкенд не нужен: данные хранятся в `localStorage` браузера. При первом запуске создаются демо-брони на сегодня и завтра. Сбросить данные — удалить ключ `meeting-room-bookings` в DevTools → Application → Local Storage.

## Стек

- **Vite + React 19 + TypeScript** (strict).
- Без UI-библиотек и state-менеджера: экран один, глобального состояния нет, серверное состояние живёт в собственных хуках.
- Модальное окно — нативный `<dialog>` (Esc, backdrop, блокировка фона из коробки).
- Стили — обычный CSS с переменными, без препроцессоров.
- Тесты — Vitest.

## Что сделано

- Выбор даты: стрелки «предыдущий/следующий день», нативный date picker, кнопка «Сегодня».
- Таймлайн дня 09:00–18:00 с шагом 30 минут:
  - свободные слоты — кнопки, занятые бронью — не кликабельны;
  - клик по брони открывает редактирование (или просмотр, если бронь уже началась);
  - превью выбранного интервала и линия «сейчас» для сегодняшней даты;
  - прошедшие слоты визуально недоступны.
- Форма создания и редактирования:
  - в «Начале» отключены прошедшие и занятые варианты, в «Окончании» — выходящие за 2 часа, конец дня или начало следующей брони;
  - подсказка с длительностью;
  - ошибки показываются под полем или баннером формы — одинаково для клиентской и серверной валидации.
- Удаление с подтверждением.
- Все состояния экрана: загрузка, пустой день, ошибка загрузки с повтором, фоновое обновление, ошибка обновления поверх устаревших данных, отправка формы, удаление.
- Обработка ответов сервера `400`, `404`, `409`, `500`.
- Адаптивность (desktop / ≤800px / ≤480px) и базовая доступность.
- 52 unit-теста на бизнес-правила и граничные случаи.

## Бизнес-правила

Все правила — чистые функции в `src/domain/booking.ts` без React и сети. Одна и та же `validateBooking(input, existing, now, excludeId?)` вызывается и в UI, и в mock-сервере; текущее время передаётся аргументом, поэтому тесты не подменяют `Date`.

| # | Правило | Реализация |
|---|---|---|
| 1 | Время в пределах 09:00–18:00 | начало ≥ 09:00 и < 18:00, окончание ≤ 18:00 |
| 2 | `start < end` | сравнение в минутах от полуночи |
| 3–4 | Длительность 30 мин – 2 ч | границы включительно |
| 5 | Нет пересечений, касание допустимо | `a.start < b.end && b.start < a.end`, только брони той же даты |
| 6 | Нельзя бронировать прошлое | прошедшая дата — нельзя; сегодня — слот должен начинаться не раньше текущей минуты |
| 7 | Бронь не конфликтует сама с собой | `excludeId` при редактировании |
| 8 | Сервер может вернуть конфликт | см. «Обработка ошибок» |

Время хранится как `HH:mm` и сравнивается в минутах, а не через `Date`: это «время на стене» без часового пояса, а `Date` добавляет пояс, летнее время и классический сдвиг `toISOString()` на день в UTC+N. Даты форматируются по локальному времени.

## Архитектура

```
src/
  domain/      бизнес-правила: типы, валидация, слоты, даты (+ тесты)
  api/         сетевой слой для UI: getBookings, createBooking, updateBooking, deleteBooking, ApiError
  mocks/       «сервер» на localStorage: хранилище, валидация, HTTP-подобные ответы
  hooks/       useBookings, useBookingForm, useDeleteBooking, useNow
  components/  DateNavigator, DayTimeline, BookingForm, ConfirmDialog
  pages/       BookingPage — собирает экран
  utils/       форматирование дат
```

Зависимости направлены в одну сторону: `pages/components → hooks → api → mocks`, и все слои используют `domain`, который ни от кого не зависит.

### Замена mock на реальный API

UI не знает о mock: компоненты и хуки работают только с функциями из `src/api/bookings.ts`. Для перехода на настоящий бэкенд меняются только тела этих четырёх функций, например:

```ts
export const getBookings = async (date: string): Promise<Booking[]> => {
  const response = await fetch(`/api/bookings?date=${date}`);
  if (!response.ok) throw new ApiError(response.status, await response.json());
  return response.json();
};
```

`ApiError` и формат тела ошибки (`{ code, message, field?, conflictWith? }`) остаются теми же.

### Mock API

Контракт из ТЗ: `GET /api/bookings?date=`, `POST`, `PATCH /:id`, `DELETE /:id`.

- задержка ответа ~300 мс, чтобы были видны состояния загрузки;
- «сервер» сам валидирует правила тем же `validateBooking`: нарушение → `400 VALIDATION_ERROR` с `field`, пересечение → `409 CONFLICT` с `conflictWith`, несуществующий id → `404`, исключение (например, недоступный storage) → `500`;
- PATCH сливает изменения с текущей бронью и валидирует итог;
- данные из `localStorage` проверяются type guard'ом: битый JSON или мусорные элементы не роняют приложение;
- чтение, валидация и запись происходят синхронно в одном шаге, поэтому две вкладки не могут обе пройти проверку и создать пересекающиеся брони.

Рассматривал MSW: он ближе к реальности (настоящий `fetch`, запросы видны в Network), но добавляет service worker и настройку для prod-сборки. Для объёма задачи выбрал более простой для ревью fake-слой с HTTP-подобными ответами; граница с UI при этом та же.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| `409` при сохранении | понятное сообщение с занятым интервалом, фоновый перезапрос списка, поля формы не сбрасываются |
| `409` + перезапрос тоже упал | сообщение в форме остаётся; над таймлайном предупреждение «данные могут быть устаревшими» с кнопкой «Обновить», старый список не пропадает |
| `404` при редактировании (бронь удалили в другой вкладке) | сообщение и кнопка «Создать как новую» с теми же данными, перезапрос списка |
| `404` при удалении | считается успехом: брони уже нет |
| `400` | ошибка у конкретного поля (или в баннере, если поля нет в форме) |
| `500` / сеть | общее сообщение, данные формы сохраняются, можно повторить |
| ошибка первой загрузки | экран ошибки с кнопкой «Повторить» |

Гонки при быстром переключении дат: каждый запрос получает порядковый номер, устаревшие ответы отбрасываются; перезапрос всегда берёт актуальную дату, а не дату из замыкания. Повторная отправка формы заблокирована.

### Как воспроизвести серверный конфликт (правило 8)

1. Откройте приложение в двух вкладках на одной будущей дате.
2. Во вкладке A выберите свободный слот и оставьте форму открытой.
3. Во вкладке B забронируйте тот же слот.
4. Во вкладке A нажмите «Забронировать» → `409`: сообщение, обновлённый таймлайн, введённые данные на месте.

Аналогично для `404`: откройте бронь на редактирование во вкладке A, удалите её во вкладке B, сохраните в A.

## Прошедшее время

- «Сейчас» обновляется раз в минуту по границе минуты и сразу при возврате на вкладку — прошедшие слоты гаснут без перезагрузки.
- Если рабочий день на сегодня закончился (после 17:30), форма создания не показывается.
- Бронь, которая уже началась, доступна только для просмотра и удаления.
- Прошедшая дата — только просмотр и удаление.

## Доступность и адаптивность

- Управление с клавиатуры; порядок Tab на таймлайне совпадает с порядком времени.
- `aria-label` у слотов и броней, `aria-pressed` у выбранных.
- Ошибки: `role="alert"` у баннеров, у полей — `aria-invalid` + `aria-describedby`; после неудачной отправки фокус переходит на первое поле с ошибкой.
- Уведомления — `role="status"`; после закрытия формы или диалога фокус возвращается на заголовок расписания.
- Фокус в форму после выбора слота, видимый `:focus-visible`, `lang="ru"`.
- Мобильная ширина: тач-цели ≥ 44px, `font-size: 16px` у полей (без зума в iOS), форма под расписанием, без горизонтального скролла на 375px; `prefers-reduced-motion`.

## Принятые допущения

- Одна переговорная, время — локальное время пользователя.
- Шаг выбора времени — 30 минут; выходные считаются рабочими днями.
- Слот, начинающийся в текущую минуту, ещё доступен (секунды не учитываются).
- Название необязательное, на клиенте ограничено 100 символами.
- При смене даты открытая форма закрывается.
- При одновременном редактировании одной брони побеждает последнее сохранение.

## Что не сделано и что бы доделал

В порядке приоритета:

1. Тесты на mock-сервер (400/404/409, битый storage) и на хуки (`useBookings`, `useBookingForm`).
2. Ограничение длины названия в `validateBooking`, чтобы правило проверял и сервер.
3. Синхронизация вкладок через событие `storage` (сейчас вторая вкладка обновляется только после своего запроса — это намеренно оставлено для демонстрации 409).
4. Дата в URL (`?date=`), чтобы ссылка и перезагрузка открывали тот же день.
5. Автопереход на новый «сегодня» после полуночи.
6. Защита от потери черновика при смене даты и оптимистичная блокировка (версия брони) против перезаписи чужих изменений.
